compile (BT-Basic)
Title: COMPILE SOURCE FILE
The compile function compiles the source code in a file and generates one or more files containing machine‑readable code. The different types of files are described below. The compiler decides which type of file to produce, based on the type of source file to be compiled, and on the options which you specify.
When the source file for an executable test is compiled, the compiler creates either a requirements file or a test object file. The requirements file contains information about the testhead resources required to run the test; Module Pin Assignment (MPA) uses this data to assign the appropriate testhead resources for the test. The test object file contains the executable code that the system uses to run the test. The requirements file is not created if the test is in a library file.
The compiled file is placed in the same directory as the source file, and is given the same name as the source file but with characters .r added to the requirements file, and .o added to the test object file. There are other optional files, as described below, and they are treated similarly to the .r and .o files. For instance, the optional list files have characters .l (for list) added to the name. As an example, if the following function is executed, and an object file is produced,
  compile "digital/u94" ; list
then the object and list files are named digital/u94.o and digital/u94.l, respectively (a requirements file would be named digital/u94.r). These files are placed by the compiler in the same directory as the source file. If a compiled file already exists, the compiler unlinks it. (Use the backup option if you do not want files automatically unlinked.)
• .o and .r files
When it compiles any kind of source file, the compiler always produces an object (.o) file, except when it generates the requirements (.r) file.
The compiler generates the .r file the first time it compiles the executable source file for a test. When MPA runs, it reads the data from all the .r files and assigns the appropriate resources for the board test. At this time, the software also generates the wirelist.o file.
When a test is subsequently compiled, the compiler regenerates the requirements data and compares that with the data in the wirelist.o file. If the requirements are the same, the compiler produces the executable .o file for the test. At that time, the compiler unlinks the .r file if one exists.
If you edit an executable test and, in doing so, change the requirements, then the compiler produces a new .r file and unlinks the .o file. In this case MPA has to be run again. If your editing did not change the requirements, then a new .o file is generated and the old one is unlinked.
• .l file
The list file is generated when the compiler's list option is specified (as above). Whether or not a listing is requested, a compile summary and any error messages are listed to the terminal; the summary always goes to the terminal and is not redirected by the printer is function.
• .d file
The debug file is generated when you compile an executable VCL source file and you specify the compiler's debug option. This file contains information correlating the vectors in the VCL test with the vectors in the order they are to be executed when the test is run. The .d file is useful when you run the debug software on the test (see also the generate debug (VCL) function).
In most cases the compile function determines the compilation type (basic, shorts, wirelist, etc.) from the type of file to be compiled. However, with some files, such as text files and digital library files, the compiler cannot determine from the file the type of compilation required. The optional keywords described in Table C-5 are used, if necessary, to identify the type of compilation required, and to pass optional instructions to the compiler (refer to the syntax and the examples to see how you use these keywords).
 
Table C-5 Optional keywords for the compile function
Keyword
Description
board
compiles a text file into the board.o file
boardxy
compiles a text file into the X‑Y data file, board_xy.o
built
instructs the compiler that a fixture has been built when the original fixture object is not available
crosscheck
crosschecks the nodes and device data during a board compile (board.o)
debug
For a digital executable file, debug provides a .d file. In the standard system the default is set to no (the file is generated only if requested); this can be changed, in the .hp3070 file, to yes (the file is always generated)—see also the generate debug (VCL) function.
fixture
compiles a text file into the fixture description file fixture.o
library
a.  indicates that the VCL test to be compiled (into <test name>.o) is a library file and not an executable file
b.  indicates that the safeguard file to be compiled (into safeguard.o) is a library file and not a board safeguard file
map
provides a .e file for the executable version of a digital test—also see the generate map (VCL) function
nobuilt
instructs the compiler that a fixture has not been built when the original fixture object is not available
testhead
testhead indicates that the configuration file to be compiled (into config.o) is the file containing the testhead configuration. If testhead is omitted, the board configuration file is compiled; this file contains the minimum configuration required to test the board.
verify
verify is used with a safeguard library file to verify that every device test in the same directory as the safeguard file is referenced in a use parameters function in that safeguard file. The compiler issues a warning for any test that is not referenced in the safeguard file.
The system software generates some object files that do not have source files: these include the fixture and wirelist object files.
If you need to see the source for these object files, use the list object function.
Syntax
For Connect Check (on Mux systems only), the compile function includes parameters to turn on learning and to specify stimulus pins or response pins. See compile Syntax for Connect Check.
For Multiple Board Versions, the compile function includes a version label parameter to specify the version of the board. See compile Syntax for Multiple Board Versions.
 
  compile <identifier>
  compile <identifier>,<error variable>
  compile <identifier>,<error variable>;<options>
  compile <identifier>;<options>
     <identifier> can be:   <file id>
                            <directory id>
        <file id> and <directory id> are <string expressions>
     <error variable> is a <numeric variable>
     <options> can be:   <compile type>
                         <compile type>,<options list>
                         <options list>
     <compile type> can be:   board
                              board, crosscheck
                              built
                              crosscheck
                              boardxy
                              debug
                              debug, map
                              fixture
                              fixture, built
                              fixture, nobuilt
                              library
                              library, verify
                              map
                              nobuilt
                              testhead
        <options list> can be:   <item>
                                 <item>,<item>
                                 <item>,<item>, . . . <item>
           <item> can be:   <backup level>
                            <experience level>
                            <list>
                            <window>
           <backup level> can be:   numbered
                                    unnumbered
                                    nobackup
           <experience level> can be:   standard
                                        advanced
                                        expert
           <list> can be:   list
                            nolist
           <window> can be:   window
                              nowindow
Parameters
<identifier>
The identifier of the source to be compiled. Except for mixed tests, this is always the id of the source file. For mixed tests, the <directory id> is required; the object is then placed in file test.o under that directory (see example below).
<error variable>
The id of an error variable.
<compile type>
Keywords with instructions to the compiler indicating some special requirement. For details, refer to the individual descriptions of each keyword, preceding the syntax.
<backup level>
When a file is to be recompiled, determines if its object file is to be backed-up first:
• nobackup no backup is made
• numbered makes up to nine backups, each numbered sequentially as <file>.1~, <file>.2~, etc. Number 1 is the most recent. When more than nine backups occur, the oldest file is discarded and the others are renumbered.
• unnumbered a single backup is made and named <file>.~.
<experience level>
Establishes the length of error messages the user receives, and can restrict the user to a subset of the full system features.
<list>
Specifies that the optional source list file is required.
<window>
Specifies whether or not a new window is to be opened when the compile starts.
Examples
  compile "wirelist"                      ! wirelist file
  compile "shorts" ; list                 ! shorts compile with listing
  compile "digital/u21", Alpha            ! digital executable file, return any
                                          ! error to Alpha
  compile "functional/ram/test" ; list    ! digital executable file with listing
  compile "my_library/ttl/7400", Problems ; library   ! digital library compile
                                                      ! with error variable
  compile "safeguard"                     ! safeguarde file located in the
                                          ! board directory
  compile "safeguard"; library, verify    ! safeguard library file, with verify
  compile "fixture"                                   ! fixture file
  compile "fixture"; fixture                          ! a text fixture file
  compile "board"; list                               ! board file, with listing
  compile "board", Problem; board, crosscheck, list   ! board text file
  compile "board_xy" ; list                           ! board_xy file
  compile "board_xy" ; boardxy, list                  ! text board_xy file
  compile "config"                                    ! board configuration file
  compile "config"; testhead                          ! system configuration file
  compile "mixed/d_to_a"        ! Compiles both source files of a mixed test:
                                ! mixed/d_to_a/analog and mixed/d_to_a/digital
                                ! and generates object file mixed/d_to_a/test.o
