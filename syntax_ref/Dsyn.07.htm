debug (BT-Basic)
Title: DEBUG A TEST
The debug function clears all current debug data, if any, and starts debugging on the specified test. This function must be executed before any debug statements can be executed. You can still execute any BT-Basic statements while debugging.
Before starting a debug session ensure that you are msi'd to the appropriate board directory and that the board data is loaded into memory (load board function).
To stop debugging one test and start another, execute a new debug function. To end debugging and clear all debug data, execute a debug end function.
The debug software automatically creates and controls its windows; when it clears the debug data for a test, it also removes all windows associated with that test.
Use the source option to start debug in the Pushbutton Debug environment. Use the nosource option to start in the BT-Basic environment. If you omit this parameter, the environment defaults to either of the following:
• A Pushbutton Debug window is selected if debug is executed from the BT-Basic command line (see General Information);
• The BT-Basic environment is selected if debug is executed from a program, such as the testplan. In this mode, debug statements can also be executed from the program.
The debug function can optionally pass parameters to the test that it executes (these are the <test Parameters> in the syntax). The parameters consist of a list of numeric variables—simple variables and arrays can be included in the list. The passed parameters are assigned, in turn from left to right, to the formal parameters, in the order the formal parameters are listed in the test being executed. The correct number of variables must be passed to the test, and each passed variable must be the same type (simple variable, array variable, etc.) as the formal variable to which it is assigned.
With single (not‑mixed) tests, the analog and digital test‑type keywords are optional. If you are running debug from the testplan, you can use these keywords to document your test. However, they are ignored by the software (i.e., the wrong keyword does not cause an error).
When parameters are passed to a mixed test, again the optional digital and analog keywords, and the semi‑colons separating the groups of parameters, are ignored by the software. Again, we recommend that you use them in the tesplan, especially with mixed tests, to document the test for debugging purposes.
When the mixed test is executed, the debug function tries to assign the parameters, in the order they are listed, to each part of the mixed test in turn. Because it ignores the semi‑colons and test‑type keywords, debug looks first at the digital part of the test and secondly at the analog part, always in that order. If either of the parts is not included in the mixed test, or does not require passed Parameters, the debug function goes to the next part of the test.
Whether or not you use the test‑type keywords in the <test Parameters>, the correct number of parameters must be passed to the mixed test. Each passed parameter must be of the same type as the formal parameter to which it is assigned.
Remember, the purpose of the test‑type keywords is to enable you to properly document your test. If you locate any of them in the wrong position in the <test Parameters>, no error occurs.
Syntax
  debug <identifier>
  debug <identifier>; <test source>
  debug <identifier>; <test Parameters>; <test source>
  debug <identifier>; <test Parameters>
     <identifier> can be:   <file id>
                            <directory id>
        <file id> and <directory id> are <string expressions>
     <test source> can be:   source
                             nosource
     <test Parameters> can be:
        <parameter list>
        digital <parameter list>
        analog <parameter list>
        digital <parameter list>; analog <parameter list>
           <parameter list> can be:  <parameter>
                                     <parameter>,<parameter>
                                     <parameter>,<parameter>, . . . <parameter>
              <parameter> is a <numeric variable>
Parameters
<identifier>
The path name, with respect to the board test directory, of the file containing the source code of the test that is to be debugged. For mixed tests only, specify the name of the directory containing the analog and digital test files.
<test Parameters>
One or more variables passed to the tests to be debugged.
Examples
     debug "analog/r126"                     ! analog resistor test
     debug "u24"; source                     ! select Pushbutton Debug
  ! the following two statements are equivalent
     debug "analog/func_1"; V1, V2      ! analog functional test with parameters
     debug "analog/func_1"; analog V1, V2
     debug "mixed/a_to_d"                    ! mixed test
     debug "digital/u18"                     ! digital device, in‑circuit test
     debug "functional/big_ram/test"         ! digital functional cluster test
     debug "U12"; digital A, B(*); nosource
  ! the following two statements are equivalent
     debug "mixed/A_to_D"; A, B(*), C, D, X1, X2, X3
     debug "mixed/A_to_D"; digital A, B(*); analog C, D
General Information
To change the default environment when debug is executed from the command line, change the parameter in the .hp3070 file as follows.
To select Pushbutton Debug environment as the default, set:
  Debug.Source: yes
To select the BT-Basic environment as the default, set:
  Debug.Source: no
