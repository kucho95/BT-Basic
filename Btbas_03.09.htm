Break and Error Trapping
The break and error trapping statements, on break and on error, enable the normal flow of the program to be changed if the user generates a trappable break, or if an untrapped, runtime error occurs. These statements set up a branch that will be made only if and when a trappable break or error occurs—until then the program continues to run normally.
A trappable break is generated if the user presses Break to stop the program.
A trappable error is a runtime error that has not already been trapped. An untrapped runtime error is any runtime error generated by a statement which does not specify an error variable (this includes statements which can have an optional error variable parameter, but which do not).
The on break and on error statements specify delayed branches: no branching occurs when the statements are executed; instead, the statements define the type of branch that will occur if a break or an error subsequently occurs. For example:
  on error goto Fault_Routine
This statement establishes error trapping and specifies line label Fault_Routine. Until a new line label is specified, or error trapping is canceled (off error), all future untrapped errors will cause the program to branch to the line labelled Fault_Routine and continue program execution there. The on break statement is similar to on error; it causes a delayed branch if a trappable break is generated. The two statements can be active at the same time; they can specify the same or different branching activity.
The on break and on error can be changed by subsequent on break and on error statements, provided the later statements are active in the same environments in which the earlier statements are active (see below). The off break and off error statements cancel, respectively, the on break and the on error statements. When the run statement is executed, all prior break and error trapping is turned off.
There are three variations of the on break and on error statements, using the keywords goto, recover, and call. How each one operates is discussed next (only on break is described, but on error operates in the same way).
on break goto <line label>: This form of the statement is used to branch to a line that is in the same program environment; that is, the on break statement, the destination line and the actual break must all be in the main program, or all be in the same subprogram (see Subroutines and User‑definable Functions). An on break goto statement is not active in any other environment; for example, if the on break and the destination are in a subroutine, the branch will not be made if the break occurs in the main program, and vice versa.
Example 4-2 shows an example where the test operator can abort the test program at any time by pressing the Break key.
Example 4-2 Aborting the test program with Break key
  on break goto Interrupt
      . . .
    ! statements to test the board
      . . .
    print "Test Completed" | goto Finish
  Interrupt: print "Test stopped by Operator"
  Finish: end
 
on break recover <line label>: the recover enables a break in one environment to branch to a line which is either in the same environment or in a higher one (see Program Environments).
The on break statement can be in the main program or in a subprogram. When the statement is executed, it determines the actual destination line by first searching its own environment for the line, and then, if not successful, by searching the main program. If the on break statement itself is in the main program, then it is always in effect (unless canceled or temporarily overridden). If the on break is in a subprogram, then it is in effect only as long as that subprogram (including subprograms nested within that subprogram) is being executed.
In Example 4-3, a trappable break causes a branch to label Interrupt_1 as long as either the main program or subroutine Sub_B is being executed. If Sub_A is being executed, then the branch would be to label Interrupt_2.
Example 4-3 Using the "on break recover" statement
   ! Main Program
     . . .
   on break recover Interrupt_1
     . . .
     . . .
   Interrupt_1:
     . . .
   Interrupt_2:
     . . .
   end
   sub Sub_A
     on break recover Interrupt_2
     . . .
   subend
   sub Sub_B
     . . .
   subend
 
The on break call <subroutine label> are used to call a subroutine when the break occurs.
If the break would result in a recursive call (for example, the subroutine calling itself), then the call is not made; in this case, the break acts normally and breaks the program. If the on break statement is located in a subprogram, then it is active only as long as that subprogram is being executed (including calling nested subprograms).
After the exit from the subroutine which was called by the break, execution returns to the program line following the line which was being executed when the break occurred. Since a line can have more than one statement, this means that some statements in the line where the break occurred may not be executed. For example, if the line has four statements and the break occurs during execution of the second statement, then the third and fourth statements on that line will be skipped.
If an on break statement is executed in one environment, and then canceled (or overridden) in another environment, it will still be active in the original environment. For example, the following program lines contain two on break statements, one in the main program and one in a subroutine; each statement calls a different subroutine, Break1 or Break2.
Example 4-4 Using the "on break call" statement
   ! Main Program
   on break call Break1
     . . .
     call Sub_A
     call Sub_B
     . . .
   end
   sub Sub_A
     on break call Break2
     . . .
   subend
   sub Sub_B
     . . .
   subend
sub Break1
     . . .
   subend
   sub Break2
     . . .
   end sub
 
If a break occurs any time during execution of the main program or subroutine Sub_B, then subroutine Break1 is called. When subroutine Sub_A is called, the new on break temporarily overrides the original one, so that if a break occurs, then subroutine Break2 is called. After the exit from Sub_A, Break1 is again in effect.
Although this example is similar to the preceding example, they are different in that the on‑call allows a branch to a lower environment, while the on‑recover allows a branch to a higher environment.
